# Write-throughput results: 2026-08-22 WSL2

These measurements add the `rustls_openssl` variant and run every variant on the same
machine.

## Environment

- Commit: `5052b8ff5c3cfa6132a15e5b15e1630ce51a72c5`
- Kernel: Linux 6.6.87.2-microsoft-standard-WSL2, x86-64
- CPU: AMD EPYC 7763 64-Core Processor; guest allocation of 8 cores / 16 threads
- Memory: 31 GiB
- Rust: 1.97.1
- OpenSSL: 3.0.13
- CPU frequency governor: unavailable in the WSL2 guest

## Method

The full matrix ran in three separate processes:

```sh
cargo bench --bench write_throughput -- \
  --warm-up-time 1 \
  --measurement-time 2 \
  --sample-size 20
```

Each cell is the min-max of the Criterion median throughput across those processes, in
MiB/s. The shortened sampling parameters make this a development-machine comparison, not
a replacement for longer dedicated-host measurements. Only non-overlapping ranges are
treated as distinguishable.

## Comparison

Against unbuffered `tokio-openssl` on `current_thread`, `rustls_openssl` is
distinguishably faster from 64 KiB through 8 MiB: approximately 1.19x, 1.28x, and 1.26x
using the mean of the three medians. It is about 9% slower at 1 KiB, while the 16 KiB
ranges overlap.

On `multi_thread`, `rustls_openssl` and unbuffered `tokio-openssl` overlap from 16 KiB
through 8 MiB, so this run does not establish a throughput difference between them. The
rustls variant is slower at 1 KiB.

`BufWriter` remains the fastest path for 64 KiB and larger payloads under both schedulers.
The absolute values should not be compared with [the original results](original.md)
because the machine, OpenSSL version, and Criterion sampling parameters differ.
